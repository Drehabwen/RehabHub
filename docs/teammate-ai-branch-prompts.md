# 给同事的 AI 支线提示词

## 0. 使用方式

这份文档用于把同一个源码仓库交给不同同事，让他们各自使用自己的 AI 工具拆出支线方案，但仍然保持在同一个主系统叙事里。

建议使用方式：

1. 先把“总提示词”发给所有人
2. 再把对应支线提示词发给对应同事
3. 要求他们按统一格式回传结果
4. 由你做最终验收和整合

不要只发支线提示词，不发总提示词。

---

## 1. 总提示词

下面这段建议你发给所有同事：

```text
你现在接手的是同一个主项目的一个支线，不是在独立创业，也不是在做一个新的单独产品。

项目主定位固定为：
“青少年体态筛查监控中心”

当前第一核心专题固定为：
“脊柱侧弯筛查与复测”

你后续所有方案、代码建议、页面设计、功能规划，都必须服务这个主系统，而不能脱离主系统另起一套产品。

这个项目的主线必须始终保持为：
筛查 -> 风险分层 -> 报告归档 -> 复测闭环

请严格遵守以下边界：

1. 不允许把你的支线做成独立产品
2. 不允许改变项目主定位
3. 不允许把项目描述成“诊断系统”或“医疗确诊平台”
4. 你的支线必须能接回以下主系统对象：
   - 学生档案
   - 筛查工作台
   - 报告中心
   - 风险分层
   - 预警复测
5. 如果你要提出新页面、新模块或新流程，必须说明它如何服务主系统

请基于当前源码仓库进行分析，不要脱离代码臆想一个全新系统。

你的输出必须包含：

1. 支线定位
2. 这条支线服务主系统的方式
3. 当前代码里可复用的部分
4. 当前代码里需要修改或新增的部分
5. 第一阶段可执行任务清单
6. 风险与边界说明

输出风格要求：
- 直接
- 结构清晰
- 面向落地
- 不空泛
```

## 2. 给移动端同事的提示词

```text
在遵守“总提示词”的前提下，你负责的支线是：

“移动筛查执行端”

这条支线不是独立 App 产品，而是“青少年体态筛查监控中心”在现场执行场景下的移动化延伸。

目标用户：
- 筛查执行员
- 轻量复核人员

目标场景：
- 学校现场筛查
- 青训机构现场采集
- 任务执行与结果提交

你的任务是：
基于当前源码仓库，识别哪些页面、组件、状态管理和流程可以收敛成“移动筛查执行端”，并输出一个可落地的支线方案。

必须遵守：

1. 不允许把移动端做成面向普通消费者的自测 App
2. 不允许把移动端做成全量后台管理系统
3. 不允许脱离主系统的数据结构和流程
4. 必须围绕以下主系统对象展开：
   - 今日任务
   - 学生搜索 / 选择
   - 快速筛查
   - 标准筛查入口
   - 上传与提交
   - 报告归档入口
   - 复测标记

请你从源码中重点分析这些方向：
- 当前已有页面是否适合移动端收敛
- 当前 UI token 是否适合移动端
- 哪些桌面页可以裁剪为移动页
- 哪些交互必须重新设计
- 哪些模块适合优先做成 MVP

你的输出必须包含：

1. 支线名称与一句话定位
2. 目标用户与核心场景
3. 建议的移动端信息架构
4. 建议复用的现有代码文件
5. 需要新增的页面或组件
6. P0 / P1 / P2 功能清单
7. 建议的开发顺序
8. 风险与边界

如果要给代码改造建议，请优先引用当前仓库里的实际文件路径。
```

## 3. 给智能交互同事的提示词

```text
在遵守“总提示词”的前提下，你负责的支线是：

“智能交互与报告辅助模块”

这条支线不是独立 AI 产品，也不是医疗诊断机器人，而是“青少年体态筛查监控中心”中的交互增强层。

目标用户：
- 筛查执行员
- 复核人员
- 非专业阅读者
- 家长端查看者

目标场景：
- 问询补充
- 报告解读
- 筛查结果问答
- 干预建议辅助

你的任务是：
基于当前源码仓库，识别哪些页面、组件、数据结构和服务逻辑可以收敛成“智能交互与报告辅助模块”，并输出一个可落地的支线方案。

必须遵守：

1. 不允许把该支线定义为“AI 医疗助手”
2. 不允许让它承担诊断结论角色
3. 不允许脱离主系统另做一个聊天产品
4. 必须围绕以下主系统对象展开：
   - 筛查结果
   - 报告中心
   - 学生档案
   - 问询补充
   - 干预建议辅助

请重点分析：
- 当前 MedVoice 相关代码是否可以作为交互起点
- 当前报告中心是否可以承接问答与解释
- 当前建议生成逻辑是否可以变成更可理解的交互层
- 哪些页面适合加“解释 / 追问 / 摘要 / 建议”能力
- 哪些地方容易越过“辅助而非诊断”的边界

你的输出必须包含：

1. 支线名称与一句话定位
2. 目标用户与核心场景
3. 模块边界与主系统连接点
4. 建议复用的现有代码文件
5. 需要新增的交互模块
6. P0 / P1 / P2 功能清单
7. 建议的开发顺序
8. 风险与边界

如果要给代码改造建议，请优先引用当前仓库里的实际文件路径。
```

## 4. 推荐交付格式

建议你要求他们统一按下面格式回传：

```text
【支线名称】

1. 一句话定位

2. 这条支线如何服务主系统

3. 当前代码中可复用的部分
- 文件 A
- 文件 B
- 文件 C

4. 建议新增或改造的部分
- 页面
- 组件
- 数据层
- 交互逻辑

5. 功能范围
- P0
- P1
- P2

6. 第一阶段开发任务
- 任务 1
- 任务 2
- 任务 3

7. 风险与边界

8. 如果开始开发，建议优先改哪些文件
```

## 5. 你自己要补充给他们的话

你发给同事时，建议再补一句：

```text
请不要把这条支线做成新的独立产品。你输出的一切内容，最后都必须能并入“青少年体态筛查监控中心”的统一叙事中。
```

这句不能省。

---

## 6. 最后的建议

如果你要提高回收质量，建议不要只让他们“要方案”，还要让他们：

1. 给出可复用代码文件路径
2. 给出 P0 任务
3. 给出边界说明
4. 给出与主系统的连接方式

这样你拿回来的是可比较、可整合、可执行的结果，而不是两份发散脑暴。
